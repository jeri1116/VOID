# MVP 개발 방법 (초안, 방향성 확인용)

> 목적: 팀이 "무엇을 어떤 순서로, 무엇으로 만들지"를 한 번에 합의하기 위한 문서. 코드·태스크 단위 계획은 이 문서가 합의된 뒤 마일스톤별로 따로 쓴다.
> 기준: 2026-11-07 결정 사항(시민 제보 → 우선순위 지도 → 시 담당자 점검 → 조치·상태 갱신, 순찰대는 조회만).

**목표:** 시민 제보와 사전 계산 지수로 현장조사 우선순위 지도를 만들고, 담당자가 사진을 올리면 AI 판독 결과가 점수와 지도에 바로 반영되는 한 바퀴를 시연한다.

**설계 원칙:** 점수 계산은 규칙(재현 가능), AI는 "보는 일"만(사진 판독·가림·묶기·요약). 무거운 GIS 계산은 전부 해커톤 전에 오프라인으로 끝내고, 해커톤에서는 결과 파일을 읽기만 한다.

---

## 1. 기술 구성

| 층 | 1안 (권장): 파이썬 단일 서버 | 대안: Streamlit 한 장 |
|---|---|---|
| 프론트(지도) | 정적 HTML + Leaflet(빌드 도구 없음), 화면 3개: 시민 / 담당자 / 순찰대(조회) | Streamlit + folium, 역할은 사이드바 선택 |
| 백엔드 | FastAPI(제보·점검 업로드, 점수 재계산, AI 호출 대행) | Streamlit 내부 함수 |
| 저장소 | SQLite 1개 파일 + 사진 폴더 + 사전 계산 GeoJSON | 동일 |
| AI | 멀티모달 LLM API. 1차 판독·제보 묶기: Claude Haiku 5.5, 애매한 건 재판독·요약문: Claude Sonnet 5.5. 출력은 JSON 스키마 강제 | 동일 |
| 좌표 변환 | 오프라인 배치에서 EPSG:5186 → WGS84 한 번만 변환해 GeoJSON에 저장. pyproj(설치되면) 또는 GRS80 TM 역변환 공식 직접 구현(외부 라이브러리 없음) | 동일 |
| 배포 | 노트북 로컬 실행 + 휴대폰은 같은 Wi-Fi로 접속(필요 시 터널) | Streamlit Community Cloud |
| 고를 때 | 모바일 사진 업로드, 역할별 화면, 실시간 갱신이 자연스럽다 | 프론트 인력이 없거나 1일 이내 해커톤이면 이쪽. 대신 모바일 화면이 투박하다 |

API 키는 서버에만 둔다(브라우저에 노출 금지). 모델 ID·가격은 구현 시점에 공식 문서로 확인한다.

## 3. 데이터 흐름: 사전 계산 vs 실시간

| 구분 | 무엇 | 입력 | 출력 | 언제 다시 돌리나 |
|---|---|---|---|---|
| 사전 계산 | 좌표 변환, 건물 지표(노후도·용도·구조 등) | GIS건물통합정보 CSV | buildings.geojson (WGS84, 건물 ID=PNU 기준) | 원천 데이터가 바뀔 때만 |
| 사전 계산 | P(안산판 SOS 지수, 건물 단위), E(노출: 주변 주택 수·최근접빈집거리 등) | 위 + 빈집목록·최근접거리 CSV | buildings.geojson 속성, params.json(가중치·등급 경계) | 가중치 합의가 바뀔 때 |
| 사전 계산 | 격자 집계(시민 공개용) | buildings.geojson | grid.geojson (격자별 등급만, 소수 셀은 가림) | 위와 함께 |
| 실시간 | 시민 제보 접수 | 카테고리·제목·글·사진·위치 | report 행, 근처 제보 묶음(AI) | 제보마다 |
| 실시간 | 담당자 점검 | 현장 사진 | 가림 처리 → AI 판독 JSON(보이는 상태·근거·확신도) → H(위해 단계) | 업로드마다 |
| 실시간 | 점수 갱신 | P(고정) × H × E + 법정 기한 + 불확실성 가점 | 건물 점수·색(빨강/주황/초록/회색), 격자 재집계 | 제보·점검·조치 상태 변경마다 |
| 실시간 | 조치·상태 | 담당자 입력 | 상태(접수→점검→조치중→완료), AI 요약문 | 상태 변경마다 |

회색(미점검)은 H가 없는 상태이며, 불확실성 가점으로 "먼저 가볼 곳"에 끌어올린다.

## 4. 마일스톤

| # | 시기 | 마일스톤 | 완료 기준(한 줄) |
|---|---|---|---|
| M1 | 해커톤 전 | 사전 계산 파이프라인 | buildings.geojson·grid.geojson이 생성되고, 표본 5동 좌표가 지도 서비스 위치와 20m 이내로 맞는다 |
| M2 | 해커톤 전 | 점수 규칙 확정 | params.json 하나로 P·H·E·기한·가점이 정의되고, 손으로 계산한 3개 사례와 결과가 같다 |
| M3 | 해커톤 전 | AI 판독 지시문 검증 | 준비한 현장 사진 30~50장에서 JSON이 100% 파싱되고, 사람 판정과의 일치율을 한 번 측정해 기록했다 |
| M4 | 해커톤 중 | 지도 3화면 + 제보 | 시민이 휴대폰으로 제보하면 담당자 지도에 즉시 뜨고, 시민 지도에는 격자 등급만 보인다 |
| M5 | 해커톤 중 | 점검 → AI → 갱신 루프 | 담당자가 사진 1장을 올리면 30초 안에 판독 결과·점수·색이 바뀌고 순찰대 화면에도 반영된다 |
| M6 | 해커톤 중 | 시연 고정 | 시나리오 1개를 네트워크 없이(캐시 응답) 끝까지 재생할 수 있고, 녹화본이 있다 |

## 5. 역할 분담 (4명 예시)

| 역할 | 맡는 마일스톤 | 해커톤 중 주 업무 |
|---|---|---|
| 데이터·지수 | M1, M2 | 사전 계산 결과 보정, 점수 재계산 함수, 격자 공개 규칙 |
| AI | M3, M5(판독 부분) | 판독·가림·제보 묶기·요약 호출, 실패 시 대체 응답, 응답 캐시 |
| 백엔드·지도 | M4, M5(갱신 부분) | FastAPI, SQLite, Leaflet 3화면, 모바일 업로드 |
| 기획·발표 | M6, 전 구간 검수 | 시연 시나리오·데모 데이터, 개인정보 점검, 슬라이드·녹화 |

## 6. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| AI API 실패·지연·이상 출력 | JSON 스키마 검증 실패 시 1회 재시도 후 "사람 확인 필요"로 표시. 시연 사진은 응답을 미리 캐시 |
| 좌표 어긋남(5186 축 순서·원점 혼동) | 변환은 배치에서 한 번만, M1의 표본 5동 대조로 확인. 서버·프론트는 WGS84만 다룬다 |
| 개인정보(빈집 주소, 사진 속 얼굴·번호판, 제보자) | 시민 화면은 격자 등급만, 소수 셀은 숨김. 사진은 가림 후 저장, 가림 실패 시 비공개. 제보자 정보는 담당자 화면에도 최소화 |
| 데모 현장 네트워크 | 노트북 로컬 서버 + 휴대폰 핫스팟, 캐시 모드, 녹화 백업 |
| 범위 팽창(기능 욕심) | M4·M5 한 바퀴가 돌기 전에는 새 기능 금지. 순찰대 화면은 조회 전용으로 고정 |

## 7. 팀이 정해야 할 기술 결정

| # | 결정 | 선택지 | 기본 제안 |
|---|---|---|---|
| D1 | 1안 vs 대안 | FastAPI+Leaflet / Streamlit | 프론트 가능한 사람이 1명 이상이면 1안 |
| D2 | 좌표 변환 방법 | pyproj 설치 / TM 공식 직접 구현 | Python 3.14에 pyproj가 바로 설치되면 pyproj, 아니면 직접 구현(외부 의존성 0 유지) |
| D3 | 격자 크기·공개 하한 | 250m / 500m, 셀당 최소 건물·빈집 수 | 250m, 빈집 2호 이하 셀은 등급 대신 "정보 없음" |
| D4 | 사진 가림 방식 | LLM이 영역 좌표 반환 → 서버에서 블러 / 로컬 얼굴 검출 / 가림 없이 비공개 | LLM 영역 좌표 + 실패 시 비공개 |
| D5 | 역할 구분(로그인) | 데모용 역할 선택 / 간단 비밀번호 | 데모용 역할 선택(실서비스는 시 인증 연동으로 별도 설명) |

참고: `이전문서\reports\11 [설계] AI 분류 설계와 개발 계획.md`의 판독 JSON 스키마·위험 표는 재사용하되, 순찰대 촬영·경로 엔진·영상 판독 부분은 이번 MVP 범위에서 뺀다.
